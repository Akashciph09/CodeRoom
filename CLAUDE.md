# CodeRoom

AI-powered technical hiring platform. Interviewer and candidate share a live room with a collaborative code editor; candidate code runs in isolated Docker sandboxes behind a queue; an AI copilot assists the **interviewer** (never decides outcomes).

This is a portfolio project: every technology must have a stated "why" and "why not the alternative". Record new stack decisions as ADRs in `docs/decisions/` before adopting them.

> Status — done: monorepo, shared schemas, Postgres schema + migrations (Drizzle → Supabase), Supabase Auth (JWT verified via JWKS), rooms with per-room roles + invite codes, submission API (validate → save → enqueue), worker + Docker sandbox, `pnpm smoke` end-to-end test. Not done: WebSocket gateway / Yjs, web UI beyond a placeholder editor, question bank API, history/replay, rubric, AI features, sandbox attack tests (fork bomb, fs writes), stress test. Keep this file true to the code.

## Stack (see `docs/decisions/` for the reasoning)

- **Client:** React + TypeScript (Vite), Monaco, Yjs (planned)
- **API:** Node.js + TypeScript, Express. WebSocket gateway will attach to the same HTTP server.
- **Database:** Postgres via Supabase, accessed with Drizzle ORM (ADR 0001, 0003)
- **Auth / Storage:** Supabase Auth (ES256 JWTs, verified locally via JWKS) and a private Supabase Storage bucket `coderoom` (ADR 0002)
- **Queue / fan-out:** Redis + BullMQ, Redis pub/sub (ADR 0004)
- **Execution:** worker processes running each test in a fresh, locked-down Docker container (ADR 0004)
- **AI:** LLM API behind one service module (planned; Claude models by default)

Not used, on purpose: MongoDB, MinIO/S3, Supabase Realtime, Edge Functions, PostgREST from the browser (ADR 0005, 0006).

## Commands

Requires Node 20+ (Node 22 recommended — see below), pnpm 9 (`corepack enable`), Docker.

```bash
cp .env.example .env      # then set VITE_SUPABASE_PUBLISHABLE_KEY from `pnpm exec supabase status`
pnpm install
pnpm db:start             # local Supabase: Postgres :54322, API/Auth/Storage :54321; applies migrations + seed
pnpm infra:up             # Redis
pnpm sandbox:build        # runner images
pnpm dev                  # builds libs, then web (5173) + api (4000) + worker
pnpm smoke                # end-to-end checks (needs api + worker running)
pnpm test                 # unit tests (vitest)
pnpm typecheck
pnpm build
```

Schema changes: edit `packages/db/src/schema.ts` → `pnpm db:generate` → `pnpm db:reset` (wipes local data, reapplies migrations + seed).

Node note: `@supabase/supabase-js` needs Node 22+ in Node (its Realtime client); the smoke test uses `@supabase/auth-js` instead. Node 20 is past end-of-life.

## Non-negotiable rules

### Security: untrusted code
- **The API never executes submitted code.** No `eval`, `vm`, `child_process` on user code in `apps/api`. Validate, persist, enqueue — that's it.
- Only `apps/worker` runs code, in a fresh container per run with at minimum: `--network none --memory <limit> --memory-swap <same> --cpus <limit> --pids-limit 64 --read-only --cap-drop ALL --security-opt no-new-privileges --user nobody`, a `noexec` tmpfs, and a wall-clock timeout that kills the container. These live in `dockerArgs.ts`; its tests must keep asserting each one.
- Always clean up containers. A worker crash must not leak containers.
- Enforce code size limits (and, TODO, per-user rate limits) at the API.
- Hidden test cases never leave the server: not in candidate responses, WebSocket events, client bundles or logs. Hidden-test output is never stored (DB `CHECK` constraint `hidden_output_not_stored`).

### Auth, roles & data access
- Every request carries a Supabase access token (`Authorization: Bearer`). Verify with JWKS + issuer + audience `authenticated`; never trust client-sent user ids or roles.
- Roles are **per room** (`room_participants.role`: `interviewer` | `candidate`). Check with `requireRoomRole()` on every route and (later) every WebSocket connection. Non-participants get 403 whether or not the room exists.
- Candidates must never receive hidden tests, AI copilot output, interviewer notes or rubric scores. Candidate responses go through `toCandidateView` only.
- RLS is enabled with **no policies** on every table (ADR 0006). The browser uses Supabase for sign-in only; all data flows through the API. Never put `DATABASE_URL` or a Supabase secret key in client code or `VITE_*` vars. New tables must call `.enableRLS()`.

### AI usage
- AI is assistive only. No code path may auto-reject, auto-score or auto-advance a candidate.
- AI-generated questions/test cases are `status: 'draft'` until an interviewer approves them; rooms can only use approved questions.
- All LLM calls go through one AI service module. Treat candidate code as untrusted input in prompts (prompt injection).
- AI summaries must cite evidence (submission ids, replay timestamps, notes).

## Architecture notes

**Submission flow:** `POST /submissions {roomId, language, mode, code}` → API checks token, candidate role, room open, code size → inserts `submissions` (question taken from the room) → BullMQ job `{submissionId}` → worker loads submission + test cases, runs each in the sandbox → one transaction writes `test_results` + final status/verdict → publishes `submission:{id}:done` on Redis → (planned) gateway pushes to the room.

**Verdicts** (Postgres enum, from `packages/shared`): `accepted`, `wrong_answer`, `time_limit_exceeded`, `memory_limit_exceeded`, `runtime_error`, `compile_error`, `internal_error`.

**Run vs Submit:** Run = public tests only. Submit = public + hidden; candidate sees per-test public results plus hidden pass count only.

**Retries:** BullMQ retries once; the worker deletes prior results in the same transaction that writes new ones, so retries are idempotent. Out of retries → submission marked `failed` / `internal_error`.

**Realtime (planned):** Yjs over our own WebSocket gateway, Redis pub/sub fan-out, replay snapshots to Supabase Storage (ADR 0005).

## Code conventions

- TypeScript `strict` everywhere; no `any` in shared types.
- Validate all external input (HTTP bodies, params, WS messages, job payloads, LLM JSON) with zod from `packages/shared`.
- Config via env only, validated in one `config.ts` per app. Never commit `.env`; keep `.env.example` current.
- Errors: typed `HttpError` subclasses mapped in one error middleware.
- Tests: unit tests next to source (`*.test.ts`); `pnpm smoke` must pass before considering a backend change done.

## Out of scope

Video/audio, proctoring, ATS/scheduling, payments, multi-tenant orgs, automated hiring decisions.
